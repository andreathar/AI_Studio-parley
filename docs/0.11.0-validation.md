# 0.11.0 native work-loop validation

This runbook is historical: it was the 0.11.0 acceptance protocol for the
autonomous work loop, and a release no longer requires it. Run it in a
disposable repository with separate native Claude and Codex terminals. Keep
local integration evidence separate from live-model evidence. A passing
simulated transcript, MCP transport, or PTY test does not prove live provider
behavior.

The trial ran on 2026-09-20; its results are recorded under
[Recorded trial, 2026-09-20](#recorded-trial-2026-09-20). A rerun records the
source commit, installed package version and path, service version, native CLI
versions, operating system, wall-clock timestamps, and commands with the
evidence. Do not copy credentials into the repository or weaken native
authentication, trust, or approval settings.

## Isolated setup

Create a fresh checkout, state home, and target repository. Use the release
candidate itself for `AP`; do not mix a source checkout, installed command, and
running service from different builds.

```sh
export TRIAL_ROOT="$(mktemp -d /tmp/agent-parley-011.XXXXXX)"
export SOURCE="$TRIAL_ROOT/source"
export REPO="$TRIAL_ROOT/target"
export AGENT_PARLEY_HOME="$TRIAL_ROOT/state"
export CANDIDATE_SOURCE=/path/to/reviewed/candidate-checkout
export CANDIDATE_REF=REPLACE_WITH_40_CHAR_REVIEWED_COMMIT
export TARGET_URL=git@github.com:OWNER/agent-parley-011-acceptance.git
git clone --no-local "$CANDIDATE_SOURCE" "$SOURCE"
git -C "$SOURCE" checkout --detach "$CANDIDATE_REF"
test "$(git -C "$SOURCE" rev-parse HEAD)" = "$CANDIDATE_REF"
uv sync --locked --project "$SOURCE"
export AP="$SOURCE/.venv/bin/agent-parley"
"$AP" --version
claude --version
codex --version
mkdir "$REPO"
git -C "$REPO" init -b main
git -C "$REPO" config user.name "Parley acceptance"
git -C "$REPO" config user.email "parley-acceptance@example.invalid"
printf '# Acceptance target\n' >"$REPO/README.md"
mkdir "$REPO/checks" "$REPO/changes"
cat >"$REPO/checks/validate.sh" <<'CHECK'
#!/bin/sh
set -eu
test -s README.md
empty_tree="$(git hash-object -t tree /dev/null)"
git diff --check "$empty_tree" HEAD
for path in changes/*; do
  test -f "$path" || continue
  test -s "$path"
done
CHECK
chmod +x "$REPO/checks/validate.sh"
cat >"$REPO/Makefile" <<'MAKE'
check:
	./checks/validate.sh
MAKE
touch "$REPO/changes/.gitkeep"
git -C "$REPO" add README.md Makefile checks changes
git -C "$REPO" commit -m 'test: initialize acceptance target'
make -C "$REPO" check
git -C "$REPO" remote add origin "$TARGET_URL"
git -C "$REPO" push -u origin HEAD:main
```

Replace `CANDIDATE_REF` with the full reviewed release-candidate commit, and
ensure `CANDIDATE_SOURCE` contains it. Provision `TARGET_URL` as a fresh private
forge repository before running the commands. Create three dedicated test
issues there and save their numbers as `ISSUE_A`, `ISSUE_B`, and `ISSUE_C`.
Require each issue to add or update one nonempty file below `changes/` and run
`make check`. Make B depend on A; C remains independent. Save this plan as
`$TRIAL_ROOT/work-order.toml`.

```toml
[plan]
name = "0.11.0 acceptance"

[dependencies]
"ISSUE_B" = ["ISSUE_A"]
"ISSUE_C" = []
```

Replace the placeholders with numeric issue strings, then register the target,
configure its real check, review the plan, and add two lanes. Use existing
Claude and Codex credential profiles; `credentials add` may create dedicated
profiles without exposing their contents.

```sh
cd "$REPO"
"$AP" verify set 'make check'
"$AP" plan diff "$TRIAL_ROOT/work-order.toml"
"$AP" plan apply "$TRIAL_ROOT/work-order.toml"
"$AP" plan show --json
"$AP" participant add claude-acceptance --provider claude \
  --credentials CLAUDE_PROFILE
"$AP" participant add codex-acceptance --provider codex \
  --credentials CODEX_PROFILE
"$AP" up
"$AP" status --json
```

Launch each lane in its own visible terminal. Preserve native permissions and
approval prompts. Do not use provider flags that bypass them.

```sh
cd "$REPO"
"$AP" run claude-acceptance --repo "$REPO"
```

```sh
cd "$REPO"
"$AP" run codex-acceptance --repo "$REPO"
```

## Normal work and dependency order

Leave both terminals at native idle checkpoints with no mail. The supervisor
should publish a work offer and wake an eligible lane. Capture the corresponding
`<lane>-work.json` and `<lane>-wake-work.json` state, the native turn, the issue
claim, and `execution.progress={token,at}`. The offer has `kind`, `id`,
`issues`,
`text`, and `progress`; its `dispatch` state has `generation`, `progress`,
`state`, `attempts`, `last_result`, and `updated_at`.

Confirm A and C are initially actionable and B is not. After the owner of A
makes actual progress, finishes the change, runs the repository check, commits,
and reports commit-bound evidence, integrate it from the base checkout:

```sh
"$AP" participant pause OWNER_OF_A
```

Stop that lane's native terminal at its clean idle checkpoint. Pausing first
prevents pending mail from automatically restarting it while integration is
in progress. Keep its ready issue claim until verified integration completes.

```sh
"$AP" participant merge OWNER_OF_A --preview
"$AP" participant merge OWNER_OF_A
"$AP" plan show --json
"$AP" participant resume OWNER_OF_A
```

The ledger may mark A `complete` only after the exact source commit is
integrated, the configured gate passes, and the claim generation still matches.
B becomes actionable only then. A released partial claim, a closed but unmerged
forge issue, or an old `ready` report must not unlock B. Confirm the owner gets
the next eligible issue without hand-written mail.

Record distinct timestamps and generations for offer, wake, native turn, claim,
progress, recovery, and completion. Do not collapse these into one "worked"
timestamp.

## Live owner with capacity exhaustion

This scenario exercises explicit recovery while the native owner process is
still alive. The 0.11.0 release trial may use a schema-validated simulated
capacity observation, but label it **simulated capacity** in the evidence. A
separate real-provider refusal is required before claiming live quota handling
works.

1. Give one lane an issue, wait for a recorded progress token, and begin a
   native turn that remains visibly `working`. Keep the process alive. Do not
   simulate this by changing its activity file: recovery must refuse a paused
   lane, native approval wait, or operator-input idle checkpoint.
2. In its worktree, create one staged change, one unstaged change, and one
   untracked file. Record `git status --porcelain=v1` and file hashes.

   ```sh
   printf 'staged\n' >staged.txt
   git add staged.txt
   printf 'unstaged\n' >>README.md
   printf 'untracked\n' >untracked.txt
   git status --porcelain=v1
   sha256sum staged.txt README.md untracked.txt
   ```

3. With the owner still active, record the simulated observation through the
   public API. This supplies every required field and reads the native session
   identity from Parley's activity record instead of editing private state.
   Replace the example owner and issue number with the current claim.

   ```sh
   export OWNER=claude-acceptance
   export ISSUE_NUMBER=101
   "$SOURCE/.venv/bin/python" - \
     "$AGENT_PARLEY_HOME" "$REPO" "$OWNER" <<'PY'
   import json
   import sys
   import time
   import uuid
   from pathlib import Path

   from agent_parley import checkpoints, supervision
   from agent_parley.cli import Bridge

   home, repo, owner = Path(sys.argv[1]), Path(sys.argv[2]), sys.argv[3]
   directory = Bridge(home).project(repo)[1]
   session_id = checkpoints.activity(directory, owner).get("session_id")
   if not session_id:
       raise SystemExit("owner has no published native session")
   observation = {
       "state": "exhausted",
       "observed_at": time.time(),
       "reset_at": None,
       "source": "acceptance-simulated-capacity",
       "session_id": session_id,
       "observation_id": f"acceptance-{uuid.uuid4().hex}",
   }
   saved = supervision.record_capacity(directory, owner, observation)
   print(json.dumps(saved, indent=2, sort_keys=True))
   PY
   ```

   Wait for the next supervision pass, then inspect the published candidate
   through its reader:

   ```sh
   "$SOURCE/.venv/bin/python" - \
     "$AGENT_PARLEY_HOME" "$REPO" "$ISSUE_NUMBER" <<'PY'
   import json
   import sys
   from pathlib import Path

   from agent_parley import supervision
   from agent_parley.cli import Bridge

   home, repo, issue = Path(sys.argv[1]), Path(sys.argv[2]), sys.argv[3]
   directory = Bridge(home).project(repo)[1]
   candidate = supervision.published_stranded_claim(directory, issue)
   if candidate is None:
       raise SystemExit("candidate not published; wait for supervision")
   print(json.dumps(candidate, indent=2, sort_keys=True))
   PY
   ```

   Confirm it contains the same `issue`, `owner`, `session_id`,
   `observation_id`, `source`, `reset_at`, and eligible peer list.
4. From the base checkout, opt in to stopping that exact owner and claim:

   ```sh
   "$AP" issue recover ISSUE_NUMBER --reason "0.11.0 simulated capacity trial"
   ```

5. Let the supervisor call `recovery.quiesce_authorized(directory, manifest)`.
   It must re-read the authoritative candidate and matching
   `recovery/issue-N-CLAIM-approval.json`, revalidate the PID and process start
   ticks, stop the owner, capture its checkpoint, and only then publish the
   orphan marker. No approval, mismatched observation, or elapsed timeout may
   stop the process or transfer ownership.
6. Leave the eligible peer at a native idle checkpoint. Observe the orphan
   announcement arrive as unread mail, wake that peer, and tell it to run
   `agent-parley issue claim ISSUE_NUMBER --take-orphaned`. The native peer must
   execute that command and continue the remaining step. A human running the
   same command from a lane is a diagnostic fallback and does not pass the
   autonomous-takeover row.

Confirm the record names `taken.checkpoint` and the recovery receipt, the
destination contains the staged, unstaged, and untracked state with matching
hashes, and only the unfinished step remains. Keep the private checkpoint
`.bundle` and metadata `.json` as trial artifacts; do not publish their
contents.

A later provider timestamp alone must not clear exhaustion. For Codex, a changed
session needs a newer successful native event with positive per-request token
usage; within one session, cumulative usage must increase. Replayed totals,
missing or zero request usage, silence, and refusals preserve the exhausted
state. When its deadline passes, a structured reset records the lane as
available. An unknown quota state remains unknown rather than available.

## Killed owner, restart, and stale fencing

Repeat the dirty-worktree setup on another claimed issue. Record the session PID
and process start ticks, terminate that native owner, and restart the Parley
service before takeover:

```sh
"$AP" participant pause OWNER
kill -TERM OWNER_SESSION_PID
"$AP" down
"$AP" up
"$AP" status --json
```

Pausing prevents a detached restart while retaining the claim and dirty work.
Wait for the configured `stalled_after` grace period before expecting an
orphan. Its default is 600 seconds; an isolated trial may configure shorter
`interval`, `inactive_after`, and `stalled_after` values in
`$AGENT_PARLEY_HOME/supervision.json`. Record those values in the evidence.

The dead-owner poll must revalidate the PID and start ticks, capture the
checkpoint, and only then publish the orphan. Leave the peer idle and observe
the orphan mail wake its native terminal. The peer must run
`issue claim ISSUE_NUMBER --take-orphaned` itself. Confirm there is exactly one
current owner and one claim generation, the destination preserves all three
forms of working-tree state, and the new lane continues from the recorded next
action. A human claim is useful for diagnosis but does not pass this scenario.

Resume the old participant and reconnect its native session after takeover.
Its hook must refuse
the old claim as `stale_generation`; it must not edit the repository, advance
progress, complete the issue, or regain ownership. Record the old and new claim
IDs and the refusal.

## Visible waits and bounded no-progress

Exercise each wait while watching both the native terminal and durable state:

- Leave a harmless native action at an approval prompt. The supervisor reports
  `waiting for approval`, does not inject input, and does not count a wake.
- Type a partial prompt without pressing Enter. The supervisor reports
  `busy:input`, preserves the text, and does not count the refusal as an
  attempt.
- Run `"$AP" participant pause LANE`, confirm work and tool calls remain paused
  with the session and claims intact, then run
  `"$AP" participant resume LANE` and confirm work resumes on a real condition.
- Make every provider observation exhausted or unknown. Confirm no lane is
  described as having known capacity and no issue changes owner from timeout
  alone. A reached structured reset records `available`; a verified later
  success may also make the lane eligible.
- Hold the work `id` and progress token unchanged. Count at most three admitted,
  spaced wake attempts. The durable dispatch state must become `escalated` with
  a named `last_result` and visible next action. `busy:turn`, `busy:input`, and
  `busy:repeat` do not consume the bound. Restarting the service must not erase
  the attempt count or manufacture progress.

Run `"$AP" run LANE --resume --repo "$REPO"` only from a clean native idle
checkpoint. Confirm an active turn, approval prompt, or partially typed input is
left for the operator.

## Recorded trial, 2026-09-20

Environment: Linux 6.8.0-139-generic, `tmux 3.4`, `claude 2.1.270`,
`codex-cli 0.153.4`, state home outside the target repository, target repository
created fresh for the trial. Lanes ran in detached `tmux` sessions so the
operator could read each native terminal and answer its own prompts. The trial
started at source commit `7ec47d7` and finished at `9dd9d99`; two defects found
during the trial were fixed and re-verified live before it ended.

### Local evidence

- `make check` at `9dd9d99`: 1254 passed, 2 skipped, exit 0.
- Focused list from this runbook at `9dd9d99`: 94 passed, exit 0, covering
  `tests/test_autonomous_work_loop.py`, `tests/test_lane_lifecycle.py`,
  `tests/test_lifecycle.py`, `tests/test_offer_wake.py`,
  `tests/test_orphaned_claims.py` and `tests/test_work_offer.py`.

### Live-model evidence

Normal work and dependency order. A Claude lane took the work offer, claimed
issue A with claim `d5e9734055bd4cb5`, committed `46f1df2`, and the operator
integrated it as `717e6db`; the ledger recorded `complete` with
`integrated_commit 717e6dbe`. Issue B cleared its `blocked_by` only after that
integration, and issue C ran independently on a second Claude lane.

Idle dispatch. Offer `37cf782ddcb8ee65` reached an idle, fit lane and recorded
`{"attempts": 1, "result": "accepted"}`; a native tool call followed 3.2 seconds
later with no operator keystroke.

Killed owner and recovery, twice. The first owner was killed mid-work. After
`stalled_after` the claim was published as orphaned
(`claude-acceptance:55ee2fc8b0114677:1789895571`, reason "no running session
process and has been silent for 91s", reservations `["changes/b.md"]`) and the
orphan notice was delivered to every other lane. One peer read the notice and
ran `issue claim --take-orphaned` itself; `recovery.preflight` refused it
because that peer's worktree still held un-integrated work, which is the guard
behaving correctly. A clean lane completed the takeover. The second killed owner
was recovered end to end by a native peer: the peer read the orphan mail, named
the exact command, and on the operator's answer ran
`issue claim 2 --take-orphaned`, became the single owner, and continued the
work. Staged, unstaged and untracked work survived both recoveries byte for
byte:

```
9ac007af3de930baf647288da0c843b26a5f046a3fe1351f1bb039b242d22cdf  staged.txt
adba4e6eb7932efce7c5617279590ec2de9e01280dec7b245913fe85f3613fbe  README.md
528eee7ba2c0adea12842fd3eab1088d4d8402d115182154b0baef559f2164f2  untracked.txt
```

Stale fence. The killed session was reconnected. Its hooks were answered with
`decision: block`, `reason_class: stale_generation`, and the activity reason
"ownership generation transferred". It made 14 refused attempts and then went
quiet without changing progress or ownership.

Visible waits. A native approval prompt left the lane unfit with the reason
"it is waiting for a native approval", and no input was injected. A partially
typed line was refused as `busy:input` with the text preserved. A non-idle lane
was refused as `busy:turn`. A paused lane was refused as `busy:stale` and
accepted again after `participant resume`.

No-progress bound. A lane that took no action recorded `attempts: 3` and then
`manual attention required: work offer 42ca53124b90ccf0 for #2 made no progress
after 3 wake attempts`, with `escalated_at` and a named next action. Busy
refusals during the same period left `attempts` at `0`.

Capacity. Two Claude lanes recorded real `available` observations with
`source: claude-session-record` and distinct `observation_id` values. The Codex
lane held `state: "unknown"` with an empty `source`, and its claim was not moved
by timeout alone. Operator authorization for quiescing an alive owner was
recorded exactly as specified: `issue recover 3 --reason ...` stored
`session_pid 2618502`, `session_ticks 9322117`, `authorized_by operator`.

### What did not pass, and why

- **Live Codex.** The Codex account hit a real usage limit during the trial
  ("You've hit your usage limit", reset stated as 26 September 2026). No Codex
  turn could run afterwards, so cross-provider dispatch is unverified for
  0.11.0. Nothing in this row was simulated to fill the gap.
- **Capacity opt-in.** The orphan-mail half passed, live. The other half needs
  an alive owner with a recorded exhausted observation, which only the
  quota-blocked Codex account could produce, so the quiesce path remains
  verified by local tests only.
- **Capacity visibility.** `available` and `unknown` were observed live and stay
  distinct. A project in which every observation is `exhausted` could not be
  produced live for the same reason.
- **Installed rollout.** Completed after publication; see below.

### Installed rollout

Repeated against the published release, from a clean virtual environment with
no source checkout on its path:

- The service started from the same build and reported

- A native lane started there recorded `launcher_pid 3200348` and

### Defects found by this trial

- #342: a Claude lane recorded no native session identity when its hooks had no
  controlling terminal, so it was never fit for work. Fixed in `480e32d` and
  re-verified live: the lane recorded `launcher_pid`, `launcher_ticks`,
  `session_pid` and `session_ticks`, and its fit check turned true.
- #343: an admitted wake left its prompt unsent in the native composer, because
  the text and its carriage return arrived in one write and read as a paste.
  Fixed in `7ec47d7` and re-verified live.
- #344: a string sequence the terminal itself emits was read as typed input, so
  an idle lane with an empty composer refused every wake as `busy:input` and
  never escalated. Observed on two consecutive supervision passes 111 seconds
  apart; one Return keystroke cleared it. Fixed in `9dd9d99` and re-verified
  live: a lane started the same way accepted its first wake with no keystroke
  and reached `working` within seconds.
